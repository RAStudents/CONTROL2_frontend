# CONTROL — техническое задание (семестр)

Веб-сервис учёта Edge-устройств, приёма событий с объектов и отчётности для компаний-заказчиков.

Сделать нужно **только то, что описано в этом файле**. Чего здесь нет — в сдачу не входит и в интерфейс не добавляется.

---

## 1. Результат

Работающий веб-сервис (клиент + сервер), в котором можно:

1. Зарегистрироваться и войти (email + пароль, вход через Яндекс ID).
2. Разделить данные по **компаниям**: события и устройства одной организации недоступны другой.
3. Вести **реестр устройств** (имя, серийный номер, токен API, состояние связи).
4. Вести динамические справочники **привязок** (где стоит устройство: линия, ТС, зона…) и **статусов/кодов** событий.
5. Принимать с устройства (или эмулятора) JSON-события и медиа по защищённому API.
6. Смотреть **ленту событий**, открывать карточку события с кадром.
7. Работать ролями: администратор поставщика, администратор компании, наблюдатель.
8. Видеть, в сети устройство или нет (heartbeat).
9. Строить отчёты: по статусам, по событиям, каркас план/факт; выгружать CSV.
10. Писать историю действий (кто завёл устройство, кто выгрузил отчёт и т.д.).

В репозитории — **эмулятор устройства**: шлёт heartbeat, события и кадры так же, как живое железо. Без него сдать нельзя.

Документация к сдаче: README (как поднять), `docs/TELEMETRY_CONTRACT.md`, OpenAPI, Docker Compose.

## 2. Пользователи и роли

Платформа — кабинет **компаний**, не общая публичная лента.

| Роль | Компании | Устройства, токены, справочники | Лента и отчёты | Пользователи компании | Завести / заблокировать компанию |
|------|----------|----------------------------------|----------------|-----------------------|----------------------------------|
| Администратор поставщика | все | да (в рамках выбранной компании) | да | да | да |
| Администратор компании | только своя | да | да | да | нет |
| Наблюдатель | только своя | нет | да (только чтение) | нет | нет |

Права проверяются **на API**, не только скрытием кнопок.

Администратор компании приглашает людей по email или логину. У приглашённого в кабинете видна своя компания.

Самостоятельная регистрация «с улицы» либо недоступна, либо создаёт заявку, которую подтверждает администратор поставщика. Итог один: без компании пользователь не видит чужой парк.

## 3. Сущности

| Сущность | Что это |
|----------|---------|
| Пользователь | Аккаунт |
| Компания | Заказчик, граница данных (тенант) |
| Устройство | Единица парка, ходит в API по токену |
| Тип привязки | Вид места (линия, ТС, кухня, кабинет…) |
| Привязка | Конкретное место в компании («Линия 1») |
| Статус (код) | Тип события (норма, брак, нет каски…) |
| Событие | Факт с устройства: время, код, устройство, привязка, payload |
| Медиа | Кадр или короткий клип к событию |
| План | Плановое задание на привязку и день |
| Событие истории | Кто / что / когда в кабинете |

Типы привязок и коды статусов **не зашиваются в код** под одну отрасль. Новый тип/код — запись в справочнике компании (или шаблон, который копирует администратор поставщика).

Одно устройство в семестре привязано **к одной** привязке.

## 4. Контракт данных

Это сердце задания. Кабинет без стабильного JSON с устройства — не продукт.

### 4.1. Токен устройства ≠ сессия человека

События и heartbeat принимает API с **токеном устройства**. Логин сотрудника сюда не подходит.

Администратор компании (или поставщика) выпускает и отзывает токен. Отзыв немедленно закрывает приём от этого устройства.

### 4.2. Событие (минимум полей)

Поля зафиксировать в `docs/TELEMETRY_CONTRACT.md` в **первую неделю**. Ниже — обязательный минимум, имена можно уточнить, смысл нельзя выкинуть:

```json
{
  "schema_version": "1",
  "device_id": "uuid-устройства",
  "occurred_at": "2026-09-17T10:15:00+05:00",
  "code": "DEFECT",
  "confidence": 0.91,
  "idempotency_key": "device-uuid:2026-09-17T10:15:00:a1",
  "payload": {}
}
```

- `occurred_at` — время **на устройстве** (не только время приёма на сервере).  
- Сервер дополнительно хранит `received_at`.  
- `code` сопоставляется со справочником статусов компании. Неизвестный код **не отбрасывается**: событие сохраняется с пометкой «не сопоставлено».  
- Повтор с тем же `idempotency_key` не создаёт второе событие.  
- Устройство может прислать пачку **задним числом** (после обрыва связи).

Версия схемы (`schema_version`) обязательна. Ломать поля без новой версии нельзя.

Платформа **не крутит нейросеть**. Модель работает на устройстве; CONTROL принимает уже готовый факт.

### 4.3. Heartbeat

Отдельный вызов (или тот же канал — решить в контракте и описать): устройство раз в N секунд сообщает, что живо. N задаётся в контракте (например 30 с). По heartbeat считаются состояния: в сети / нет связи / ещё ни разу не выходило.

### 4.4. Медиа

К событию можно приложить jpeg (обязательно) и короткий mp4 (желательно). Лимиты размера — в README.

Доступ к файлу только внутри компании. Прямая ссылка без проверки тенанта — несдача.

### 4.5. План / факт

**План:** запись «привязка + дата + число / текст задания». Ввод в UI и/или CSV.  
**Факт:** агрегация событий за ту же дату и привязку.  
**Отчёт:** таблица план vs факт и отклонение.

Заложить **входящий** HTTP-эндпоинт «принять плановые задания» (как будто из внешней учётной системы). Живой SAP/1С не требуется. Достаточно OpenAPI + приём JSON/CSV моком.

### 4.6. Эмулятор

Каталог в репозитории (`apps/emulator` или аналог):

- логин токеном устройства;
- heartbeat;
- отправка событий из файла/CLI;
- отправка кадра;
- режим «накопил офлайн — выгрузил пачкой».

Эмулятор ходит в те же эндпоинты, что описаны в OpenAPI. Отдельный «секретный» путь только для демо — нельзя.

## 5. Состояния устройства и компании

**Устройство:**

```
ещё ни разу не выходило → в сети
                         → нет связи
```

«Нет связи», если heartbeat просрочен (порог описать в README, например 3 интервала).

**Компания:** активна / заблокирована.

Администратор поставщика может **заблокировать** компанию: лента, отчёты и выгрузки для её пользователей гаснут (понятное сообщение). Приём телеметрии на усмотрение: либо пишется в изоляции без показа кабинету, либо отклоняется с понятным кодом — **выбрать одно и зафиксировать** в TELEMETRY_CONTRACT.md.

Других статусов «для красоты» не вводить.

## 6. Функциональные требования

### 6.1. Аккаунт

- регистрация и вход: email + пароль;
- вход через Яндекс ID (ключи выдаёт заказчик; пока ключей нет — работает почта);
- профиль: отображаемое имя, выход;
- пароли не хранятся открытым текстом;
- повторный Яндекс не плодит второго пользователя.

Восстановление пароля желательно. Если нет — строка в Known limitations.

### 6.2. Компании

- администратор поставщика создаёт компанию и первого администратора заказчика;
- все сущности ниже несут `company_id`;
- чужая компания недоступна по прямому ID (IDOR — несдача);
- список компаний — только у поставщика.

### 6.3. Устройства

- CRUD в рамках компании;
- серийный номер, имя, тип (свободная строка или простой справочник типов железа — не отрасли);
- выпуск / отзыв токена;
- карточка: состояние связи, последний контакт, привязка;
- таблица парка с фильтром по привязке и состоянию.

### 6.4. Привязки

- CRUD типов привязки;
- CRUD экземпляров («Линия 1»);
- назначение устройства на экземпляр;
- новый тип без изменения кода приложения.

### 6.5. Статусы (коды)

- CRUD: код, имя, критичность (как минимум: норма / инцидент / служебное);
- лента и отчёты показывают человекочитаемое имя, если код сопоставлен.

### 6.6. Лента событий

- карточка: время, привязка, код, устройство;
- фильтры: период, привязка, код, критичность, устройство;
- пагинация;
- пустое состояние: «событий ещё нет».

### 6.7. Карточка события

- атрибуты пакета, время на устройстве и время приёма;
- превью медиа;
- **нельзя** рисовать и двигать разметку на кадре — только просмотр.

### 6.8. Отчёты

- **Статусы:** сколько событий каждого кода за период, разбивка по привязкам; простая визуализация (столбики или таблица с долями).  
- **События:** выборка ленты с группировкой (сутки / привязка / код).  
- **План/факт:** §4.5.  
- Экспорт CSV (все три). Кнопка у администратора компании и поставщика; наблюдатель — только просмотр, без выгрузки **либо** с выгрузкой, если явно решите иначе и опишете. Рекомендация: выгрузка только администраторам.

### 6.9. История

Лента в карточке устройства и компании: создание устройства, отзыв токена, смена привязки, приглашение, выгрузка отчёта, блокировка компании.

Не нужен diff каждого JSON. Нужны факты действий: кто, что, когда.

## 7. Нефункциональные требования

- OpenAPI: и кабинет (JWT пользователя), и шлюз устройства (токен).  
- `docker compose up` поднимает веб, API, БД, хранение файлов.  
- Основная поверхность — десктоп. Мобильная вёрстка не требуется.  
- Ошибки в UI — понятные, на русском.  
- Пустые экраны: нет компаний / нет устройств / нет событий / нет плана.  
- Безопасность: пароли хэшируются; нет IDOR между компаниями; токен устройства не равен правам администратора; XSS в именах привязок и payload не исполняется.  
- Запись телеметрии не должна ронять кабинет на пачке из сотен событий (достаточно очереди внутри процесса или отдельного воркера — как решите, но UI живой).

Стек команда выбирает сама, если закрыт этот файл. Рекомендация: TypeScript на вебе, API с OpenAPI, PostgreSQL, файлы в volume. Устройствам всё равно, на чём бэкенд: они шлют JSON.

## 10. Сценарии сдачи

Прогон на чистом `docker compose up`.

**A. Поставщик и заказчик**  
Поставщик создаёт компанию и администратора → администратор заводит тип привязки «Линия», экземпляр «Линия 1», устройство, копирует токен → эмулятор шлёт heartbeat, события и кадры → наблюдатель видит ленту и карточку с фото → администратор строит отчёт по статусам и скачивает CSV.

**B. Изоляция**  
Две компании. События первой не видны пользователю второй. Запрос к ID чужого устройства/события — отказ. Наблюдатель не выпускает токен и не меняет справочники (проверка API).

**C. Связь и план**  
Эмулятор замолкает — устройство «нет связи». Снова пингует — «в сети». Администратор вводит план на день по «Линия 1», события за день дают факт, таблица план/факт на экране. Поставщик блокирует компанию — кабинет заказчика не отдаёт ленту/выгрузки.
